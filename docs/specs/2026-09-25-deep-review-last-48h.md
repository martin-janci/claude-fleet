- **Linear fetch: one missing or forbidden issue in a chunk fails the whole fetch (Query.issue is non-null, so data is null)** — `crates/fleet-core/src/service/trackers/linear.rs:134` · tracker-providers
  fetch() batches up to 25 aliased `issue(id:)` lookups in one query and relies on 'a missing issue is a per-field error next to the others' data'. Linear's schema declares `issue(id: String!): Issue!` (non-null; verified in linear/linear packages/sdk/src/schema.graphql), so per GraphQL null propagation an 'Entity not found' or FORBIDDEN error on any alias nulls the root `data`. gql() then returns Err(Invalid(<error message>)) for the entire chunk, so no reference in it gets an answer. The fixture testdata/linear/fetch_two.json (`"i2": null` beside populated `data`) encodes a shape Linear cannot produce, and tests_linear.rs script_fetch asserts on it.
  *Scenario:* A user types `ENG-9999` (a known prefix, non-existent number) in a prompt. It becomes an unbound ref; sync step 3 (sync.rs:313) fetches it together with every other unbound key of the tracker. Linear answers `{"errors":[{"message":"Entity not found: Issue..."}],"data":null}`; gql() returns Err(Invalid), `provider.fetch(&refs).await?` aborts run_tracker, record_failure stores the error, and steps 3/5 (bind) are skipped. Because the abort never yields Fetched::Unavailable, unknown_keys is never populated for ENG-9999, so every later pass repeats the failure: no bare key of this tracker binds again until the bad ref is removed by hand. The same happens in step 2 when any linked Linear issue is deleted or moved to a team the key cannot read (every pass fails before step 3). A live `work { lookup }` of a missing key (fetch_one) reports 'unexpected answer from the tracker' instead of not-found.
  *Fix:* In gql(), when `data` is null and every error has a `path`, return the per-path errors instead of failing (or treat `INVALID_INPUT`/`FORBIDDEN` with a path as 'those aliases are unavailable'). Simplest robust option: on such a chunk failure, re-issue the lookups one per request (or use `issues(filter: { id: { in: [...] } })` / `issues(filter: { identifier ... })`, which is a nullable connection and never nulls the root) so a missing issue maps to Fetched::Unavailable. Fix the fixture to Linear's real shape (`data: null` + errors) and assert that the other two references still come back Found.

- **WAL sidecar files (state.db-wal / state.db-shm) are created before the chmod 600 and stay world-readable with the bearer tokens in them** — `crates/fleet-core/src/store/mod.rs:148` · critic
  PR #272 (commit 2d7415f, merged after HEAD as 61e2504) makes open_with_bus run `PRAGMA journal_mode = WAL` and migrate() right after `Connection::open` (working tree mod.rs:147-148; in 2d7415f the pragma is the line after the open). Both callers chmod state.db to 0600 only AFTER open_with_bus returns (src-tauri/src/lib.rs:127 open, :140 set_private_mode; crates/fleet-hub/src/serve.rs:63 open, :70 set_private_mode). SQLite creates -wal and -shm with the main file's mode at the moment it creates them, and never re-chmods them, so on a fresh database they inherit the umask-derived 0644 and keep it for the life of that process (and across a crash, because a leftover -wal is reused, not recreated). In WAL mode every recent commit lives in the -wal until a checkpoint: the MCP master token, hub pairing/client tokens, peer link tokens and tracker_secrets are exactly the rows written right after first open. The hub is shielded only when its data-dir chmod 0700 (serve.rs:53) succeeds or the systemd umask 0077 applies; the desktop's data dir is create_dir_all with the default mode (src-tauri/src/bootstrap/env.rs:13), so on a Linux desktop the sidecars sit 0644 in a 0755 directory. docs/hub.md:1914 promises 'state.db … Written 0600 … same as the desktop' and scripts/hub-e2e.sh:159 checks only state.db, so neither the promise nor the test covers the files that now hold the data.
  *Scenario:* First launch of the desktop on a shared Linux box (umask 022): open_with_bus creates state.db 0644, switches to WAL (creating state.db-shm 0644), migrate() writes the schema (creating state.db-wal 0644), then lib.rs:140 chmods only state.db. The user enables the control API (token written to settings) or pairs a hub / connects a Jira tracker (client token, tracker_secrets). Those rows sit in ~/.local/share/claude-fleet/state.db-wal, mode 0644, until the app exits cleanly; any other local user can `sqlite3 -readonly`-free `strings state.db-wal` and read the bearer token. If the app is killed (SIGKILL, power loss, crash) the -wal survives with 0644 and the next launch reuses it, so the exposure persists across restarts. Reproduced with python sqlite3 in a scratch dir: after `PRAGMA journal_mode=WAL` + one write + `chmod 600 state.db`, `state.db 0600, state.db-shm 0644, state.db-wal 0644`; only after the last connection closes and reopens do the sidecars come back 0600.
  *Fix:* Create state.db owner-only BEFORE the connection is opened: in open_with_bus (or in both callers) `OpenOptions::new().create(true).write(true).mode(0o600).open(path)` (or set_private_mode on an existing file) and only then `Connection::open`, so the pragma and migrate() create -wal/-shm from a 0600 main file; additionally chmod `<path>-wal` and `<path>-shm` after tune_file_connection for databases that already existed with a wider mode. Extend scripts/hub-e2e.sh:159 to check the -wal/-shm modes while a daemon is running, and amend docs/hub.md:1914 to name the sidecars.

- **curl script ignores a non-zero curl exit once an HTTP status was seen: a truncated or empty body is returned as a 2xx** — `crates/fleet-core/src/net/via_host.rs:234` · net-transport
  `rc=$?` is consulted only when `%{http_code}` is `000`. curl reports the real status code whenever the head arrived, so `--max-time` expiring mid-body (exit 28), `--max-filesize` refusing the body (exit 63, `rb` empty), a recv error mid-body (56) or a partial transfer (18) all print `__fleet_status__=200` plus whatever of `rb` exists, and `parse_curl` hands that back as a successful Response. The Rust side never sees `rc`.
  *Scenario:* A `via_host` Jira DC tracker fetches a 6 MiB search page. curl aborts with exit 63 before writing `$d/rb` (Content-Length > --max-filesize) and prints `200`. The script emits `__fleet_status__=200`, the headers, and an empty body. `send` returns `Response{status:200, body:[]}`; the provider's `parse_json` fails with `unreadable JSON: EOF` and the tracker records `TrackerError::Invalid("unexpected answer from the tracker")` instead of `TooLarge`. Same for a slow server: `--max-time` fires at 20 s mid-body, exit 28, status 200, half a JSON document — reported as a bad answer, not as a timeout, so the timeout branch on line 361 (`exit == "28"` -> `TransportError::Timeout`) is only reachable when no header ever arrived.

- **tidy_apply writes gc_failed timeline events to ANY session id, letting a per-host token flood and evict another org's session history** — `crates/fleet-core/src/service/work/tidy.rs:370` · orgs-isolation
